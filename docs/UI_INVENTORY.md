# UI Inventory — old `main` branch vs. `updates/v1.1`

Phase 0 of the UI revamp track. Read-only inspection of `origin/main` (mounted at `../conexus-old` as a worktree, commit `4a16708`) — the older, Next.js/Prisma-generation build of Conexus, done on Replit before the `updates/v1.1` rebuild. No code changes in this phase.

## Why most of this is DISCARD, up front

The old app and `updates/v1.1` are not the same product wearing different clothes — they're built on incompatible data models. The old app (`prisma/schema.prisma`) is a **multi-project, multi-role (6-role RBAC), section/version/approval-workflow DRHP drafting platform**: multiple companies, multiple team members per project with roles (Applicant Company / Merchant Banker / Chartered Accountant / Company Secretary / Legal Advisor / Underwriter), long-form document *sections* with versioning and an approve/request-changes state machine, an unstructured flat "Knowledge Base" fact store (`fieldKey`/`content` strings, not typed fields), background job orchestration (Inngest) for OCR/drafting/validation/export/blockchain, and an invite/notification system.

`updates/v1.1` is a **single-issuer, single-project, no-auth demo app** built around one fixed, strongly-typed `IssuerFacts` schema (`src/types/facts/`, six domains) populated by a deterministic extract → merge pipeline, with no roles, no multi-project, no long-form section drafting, no background job system beyond Supabase Edge Functions, and no notifications/invites. There is currently no login screen, no `Project` list, no user model at all — `useEnsureProject` just fetches-or-creates a single singleton row.

Given that, almost nothing in the old app has a backend to plug into today. That's expected, not a problem — see the brief. One more red flag on top of the architectural mismatch: `prisma/schema.prisma` in the old branch has an **unresolved git merge conflict** left in it (`<<<<<<< HEAD` / `=======` / `>>>>>>> origin/main` around `ICDRCorpus.embedding`) — the old branch's backend wouldn't even compile as committed. Treat everything below as read for visual/interaction ideas only, never as working reference code.

## Design assets worth salvaging

Separate from the screen-by-screen verdicts above — these are visual/token-level choices, not code.

- **Logo — keep.** `public/conexus-logo.svg` / `.png`: a real, finished brand mark (a stylized charging-bull-on-ascending-bars glyph, teal→navy gradient `#17c0a9 → #0c3d72`, navy wordmark `#0b1737`, tagline "CONNECTING INSIGHTS. DRIVING SUCCESS."). This isn't placeholder work — `main`'s own history shows a commit explicitly replacing an earlier placeholder with this asset ("Replace placeholder logo with official Conexus brand asset..."). Reuse directly.
- **Color tokens — keep the structure, reconsider the palette.** `src/app/globals.css` defines a complete semantic HSL token system (background/foreground/border/card/popover/primary/secondary/muted/accent/destructive, plus sidebar and 5 chart colors), with full light+dark pairs, wired through Tailwind v4's `@theme inline`. The *structure* (semantic naming, light/dark parity from day one) is worth using as a starting template for Phase 1. The actual palette — a fairly generic bright blue primary (`hsl(221 83% 53%)`) — reads as standard SaaS-dashboard blue, which cuts against this brief's explicit ask for something closer to a legal/audit tool. Keep the token *architecture*, don't just copy the *values*.
- **Typography — only Inter and Montserrat are real.** The font stack is declared as `'Proxima Nova', 'Montserrat', 'Inter', sans-serif`, but the Google Fonts `@import` only loads Montserrat and Inter — Proxima Nova is never actually fetched anywhere, so in practice it's silently falling through to Montserrat. Don't treat "Proxima Nova" as an established asset; it's a name in a CSS variable that was never backed by a real font load. Inter/Montserrat as a working pairing is a real, usable starting point though.
- **Interaction primitive — worth keeping.** A `hover-elevate`/`active-elevate` utility (adds a semi-transparent overlay via `::after` rather than swapping background colors directly) is a clean, reusable low-level interaction pattern independent of the rest of the app.
- **Shadow/radius scale — worth keeping.** `--radius: 0.75rem` with derived sm/md/lg/xl, and a `--shadow-2xs` → `--shadow-2xl` progressive elevation scale. Reasonable as a starting token scale regardless of final values.
- **GSAP stagger-in entrance animations — judgment call, lean against.** Recurs across Dashboard/Validation/Gaps (staggered fade+slide on card grids). Technically fine, but this kind of card-stagger motion reads as generic startup-dashboard polish, which is the opposite of what this brief asks for ("closer to a legal/audit tool... not a generic SaaS dashboard"). Don't default to carrying this forward.
- **Eligibility's CSS-3D stacked-card flow — explicitly do not carry forward.** Visually the most inventive thing in the old app, and exactly the wrong tone for a SEBI filing product per this brief. Skip it even though it's well-built; it fights the intended positioning.
