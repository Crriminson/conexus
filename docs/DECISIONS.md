# Decisions — non-obvious calls and why

Written so a fresh session doesn't relitigate these. If you think one of these is wrong, that's a legitimate conversation — just have it knowing what was already considered, not from scratch.

## Task 12 (generate-section): design choices (2026-08-10)

**Separate `generated_sections` column, not folded into `facts`.** The 3 narrative sections (Risk Factors, MD&A, Business Overview — architecture §2/§6) aren't proposed-vs-confirmed fact data — there's no `merge()` semantics to apply, no per-field status, no conflict to raise. They're regenerated wholesale on demand and simply overwritten. Giving them their own `projects.generated_sections jsonb` column (migration `20260810000000_generated_sections.sql`) keeps that distinction structural rather than papering over it with fields inside `IssuerFacts` that don't fit that shape.

**Synchronous, not async/chunked like `extract`.** `extract` needed the 202-background-task-plus-reaper machinery because a real DRHP is 200–400 pages and blows the ~150s wall-clock ceiling even per-chunk. `generate-section` is one Gemini call over a short list of already-confirmed facts (a handful to a few dozen short strings/numbers, not a document) — comfortably inside that ceiling. Building the async apparatus here would be solving a problem this function doesn't have.

**Only confirmed facts with a real `sourceDocId` are ever offered to the model** (`collectConfirmedFacts`), not just `status === 'confirmed'` alone. A confirmed field with no source (possible in principle, though `edited` is the normal path for that) can't be cited, and CLAUDE.md requires AI-generated content to always carry a citation back to its source. Filtering at the input boundary means every fact the model sees is already citable — there's no later code path that has to decide whether an uncited claim is acceptable, because the model was never given anything uncitable to begin with.

**Citations are validated server-side, never trusted from the model.** The prompt asks for `citedFieldPaths` naming exactly the fieldPaths it was given, but `resolveGeneratedSections` still drops any path that doesn't match a real offered entry before persisting. A model citing something it wasn't given would be worse than a model citing nothing — silently trusting free-text citations is exactly the kind of thing that turns "always carries a citation" into an unenforced suggestion.

**The export gate ties to Task 12 automatically, with no new gate logic.** `checkExportGate` already worked generically over every assembled section's `missingFieldPaths` (not hardcoded to "computed" sections specifically, despite its comment), so giving each not-yet-generated section a `missingFieldPaths: ['generated.<key>']` marker was enough to make export block until narrative generation has actually run — exactly the self-tightening behavior the original Task 14 entry below predicted when it said additional sections would "automatically tighten" the gate.

**`parseModelJson` was extracted from `extract/index.ts` into `supabase/functions/_shared/parseModelJson.ts`.** Both Edge Functions ask Gemini for `responseMimeType: 'application/json'` and both need the same defensive fence-stripping for when the model wraps output in ```` ```json ```` anyway. No behavior change to `extract` — pure relocation of an identical private function into a shared one, avoiding a second copy of logic that would otherwise silently drift.

**Could not apply the migration or deploy the Edge Function from this session.** This session only has the Supabase anon key (`VITE_SUPABASE_ANON_KEY`) in its environment — no service-role key, DB password, or Management API token, all of which prior sessions needed and used (see "Environment notes" in `docs/STATE.md`). The migration SQL and the function's code are both written, tested (92... now 112 Vitest tests passing, including a full mock-provider run of the generate flow), and committed — but someone with elevated Supabase access needs to actually run `supabase db push` (or apply the SQL directly) and `supabase functions deploy generate-section` before this works against the live project. See `docs/SETUP.md` for the exact commands.

**Decision:** `updates/v1.1` is source of truth going forward. No new branches off `main`. If/when a PR is opened, it's `updates/v1.1 → main`, not the reverse — `main` is behind, not a parallel line of development to reconcile with.

## LLM provider abstraction: config injected, not read from Deno.env inside providers (2026-08-09)
`callLLM.ts` already was a single seam, but the Gemini implementation read `Deno.env.get('GEMINI_API_KEY')` directly and hardcoded model/base URL as module consts — swapping providers meant editing this file's internals, and the file couldn't be unit-tested outside Deno. Split into `supabase/functions/_shared/llm/`: an `LLMProvider` interface, a `createGeminiProvider(config)` that takes `{ apiKey, model, baseUrl }` as plain arguments rather than reading env itself, a `createMockProvider()` test/dev double, and a `createLLMProvider(env)` factory that's the *only* piece touching env resolution (and even that takes an injected `EnvReader` — `{ get(key): string | undefined }` — rather than calling `Deno.env` directly, so it's constructible with a plain object in tests). This mirrors the same reasoning already applied to `merge()` relocating to `_shared/` (docs/DECISIONS.md, below): keep the Deno-only surface as thin as possible, push everything testable into plain TypeScript importable from both runtimes.
Considered keeping a single `callLLM(input, providerName?)` function with an internal `switch` instead of a provider-object interface — rejected because Task 12 (generate-section) and any future non-Gemini provider would keep adding branches to one function rather than each being an independently testable unit implementing the same contract.
`LLM_PROVIDER=mock` is a real, selectable runtime option (not just a test-only construct) — deliberately, since Step 2 of the current phase needs to exercise the app without spending Gemini quota, and Step 4 (Task 12) needs to write and verify generate-section against a mock before it ever calls the real API. It returns a valid-shape empty-facts JSON by default so it's a safe drop-in for the extraction pipeline specifically, not just a generic no-op.
`LLMFile.bytes` was typed `Uint8Array<ArrayBuffer>` instead of bare `Uint8Array` — a TypeScript 6 generic-TypedArray lib fix, not a behavior change; see docs/PROGRESS.md's Step 1 entry for detail. Surfaced only because this refactor's `src/lib/llm/` re-export pulled the Deno-side file into `src/`'s type-checked graph for the first time, the same way `merge()`'s relocation did.

## No RAG / no chunking-by-default (architecture doc, section 1)
DRHP structure is fixed, so the job is extraction into a schema, not retrieval over a corpus. Gemini's context window is large enough to take a document directly. Embeddings, vector search, and a retrieval layer were cut as pure over-engineering for this problem. This is the baseline the rest of the decisions below sit on top of — chunking (see below) is an exception forced by a platform limit, not a reversal of this call.

## Fresh Supabase project instead of cleaning up the old one
The originally-given project (`qghdelmrdnnznsqyisbm`) turned out to be the live database behind the old pre-rebuild Next.js/Prisma app — still holding its full legacy schema (17 tables: `Project`, `Document`, `User`, etc., all Prisma-cased). Rather than drop/clean that schema on a shared/ambiguous-ownership database, moved to a fresh project (`fvtazfdppcajoglteutz`). No collision risk either way (different casing), but a clean slate was simpler to reason about than auditing what else depended on the old project.

## Gemini Files API instead of inline base64
First implementation sent the document as `inline_data` (base64 in the request JSON). This has a hard ~20MB payload ceiling and, worse, held the full base64-inflated string (plus a `JSON.stringify` copy of it) in the edge function's memory — hit `WORKER_RESOURCE_LIMIT` on a 13.6MB real file. Switched to Gemini's Files API: upload raw bytes once, get a `file_uri`, reference it in `generateContent` instead of inlining. Raises the ceiling to 2GB and avoids materializing a base64 copy at all. This fixed the memory problem — it did **not** fix the wall-clock problem (see next entry); those turned out to be two separate issues discovered in sequence, not one.

## Async (202 + background task) AND chunking — not bigger timeouts
Confirmed by direct measurement that the synchronous `extract` function times out at 150.9s wall-clock on the real 13.6MB test file — not a synthetic estimate. Then confirmed via a throwaway probe function that `EdgeRuntime.waitUntil()` (Supabase's background-task mechanism) does **not** grant a new time budget — a background task dies at the same ~150s ceiling as a normal request. This means:
- There is no config knob to raise the timeout — it's a platform ceiling.
- Async (return `202`, do the work in the background, client polls) is necessary regardless, so a slow extraction doesn't block the browser/hold an HTTP connection open.
- Async alone is **not sufficient** for real 200-400 page DRHPs, whose extraction time will itself exceed 150s even in the background. Chunking (deterministic page-range splits, each an independent extract job under the ceiling, merged in via the existing conflict-detection machinery) is still required and not yet built.
This is explicitly not RAG-style chunking — no embeddings, no similarity search, no retrieval. Just splitting one document into N page ranges and treating each as its own proposer into `merge()`, which was already built to accept multiple independent proposals into one fact set.

## merge() canonical in `supabase/functions/_shared/merge/`, `src/lib/merge/` re-exports
Originally `merge()` lived only in `src/lib/merge/` (the Vite/React side) and ran client-side after the extract function returned its result over HTTP. Once extraction became async, the client is no longer involved in persisting the result — the background task itself has to call `merge()` and write to the DB. That meant the Deno runtime needed to run this code directly, not just receive its output.
Considered three options: (1) copy the logic into `_shared/` — rejected, two sources of truth for the single most correctness-critical piece of this build is exactly where subtle bugs hide; (2) import maps / cross-directory relative imports with explicit `.ts` extensions — this is what was actually done, see below; (3) duplicate everything including types — used as a narrower fallback for pure type declarations only (see next entry), not for logic.
The relocation works because both Vite (`allowImportingTsExtensions: true`, already set) and Deno accept relative imports with explicit `.ts` extensions — so `src/lib/merge/merge.ts` is now a two-line re-export pointing at the canonical file. Verified by running the existing 18 tests unchanged against the relocated implementation — that was the acceptance bar, not just "it compiles."

## Type declarations ARE duplicated (`factsTypes.ts`), logic is not
Deno can't resolve the `@/` path alias `src/types/facts` uses, and reaching those files via a relative path from `supabase/functions/` was avoided as an added layer of cross-runtime fragility on top of the merge relocation. Instead, `supabase/functions/_shared/factsTypes.ts` is a hand-maintained structural mirror of `Field`/`FieldStatus`/`IssuerFacts`/the six domain interfaces. TypeScript's structural typing (not nominal) means two independently-declared interfaces with identical shape are mutually assignable, so this works without casting anywhere. The risk this accepts: if Task 2's fact shape changes, this file must be updated by hand — nothing enforces the two staying in sync. Considered acceptable because type declarations can't have *behavioral* bugs the way duplicated logic can; a drift here surfaces immediately as a compile error at the point of use, not a silent runtime divergence.

## Optimistic concurrency (version column) over row locking
Once extraction runs as a background task — and especially once chunking makes it inherently concurrent — multiple writers can read-modify-write the same `projects` row and silently clobber each other (last write wins, earlier merge's conflicts/facts vanish). Considered `select ... for update` (a real Postgres lock) vs. a `version` integer column with compare-and-swap retry. Chose optimistic concurrency: no long-held locks from a serverless/edge function (which could die mid-transaction and leave a lock stuck), simpler to reason about, and retries are cheap since `merge()` is fast and pure. Retry loop caps at 5 attempts before giving up and marking the document `failed` rather than retrying forever.
Known gap: `useUpdateFacts` (human edits, Task 4) does not participate in this scheme yet — see `docs/STATE.md`'s open decisions.

It will render nothing until fields are actually confirmed post-extraction, which is expected and correct, not a bug to chase.

## Task 14's export gate reuses Task 11's section machinery, not a full-schema walk (2026-08-09)
"Gate on all-facts-confirmed" (architecture §9 task 14) is ambiguous on scope: every field in the entire `IssuerFacts` schema (including `company`, `litigation`, `relatedParties`, none of which Task 11 even renders), or just what the assembled document actually needs? Chose the latter: `checkExportGate()` calls the same `assembleSections()` Task 13 renders and blocks export unless every computed section's `missingFieldPaths` is empty — the identical bar the Document view already shows via its "Incomplete — N pending" badges. This keeps the gate and the on-screen status in permanent agreement (impossible for the UI to show "Ready" everywhere while export still refuses, or vice versa) and avoids requiring fields (litigation, related parties) that aren't part of this document assembly yet. If `company`/`litigation`/`relatedParties` sections are added to Task 11 later, the gate automatically tightens to match — no separate list to keep in sync.

## Polling over Supabase Realtime
Client picks up extraction progress via `refetchInterval` (3s) rather than a Realtime subscription. Realtime needs replication enabled on the table plus its own RLS policies — another moving part that can break independently, for a UX difference (3s vs. instant) nobody will notice on a document that takes 10s–150s to process. Revisit if/when the UX actually calls for sub-second updates.
