# Decisions — non-obvious calls and why

Written so a fresh session doesn't relitigate these. If you think one of these is wrong, that's a legitimate conversation — just have it knowing what was already considered, not from scratch.

## No RAG / no chunking-by-default (architecture doc, section 1)
DRHP structure is fixed, so the job is extraction into a schema, not retrieval over a corpus. Gemini's context window is large enough to take a document directly. Embeddings, vector search, and a retrieval layer were cut as pure over-engineering for this problem. This is the baseline the rest of the decisions below sit on top of — chunking (see below) is an exception forced by a platform limit, not a reversal of this call.

## Fresh Supabase project instead of cleaning up the old one
The originally-given project (`qghdelmrdnnznsqyisbm`) turned out to be the live database behind the old pre-rebuild Next.js/Prisma app — still holding its full legacy schema (17 tables: `Project`, `Document`, `User`, etc., all Prisma-cased). Rather than drop/clean that schema on a shared/ambiguous-ownership database, moved to a fresh project (`fvtazfdppcajoglteutz`). No collision risk either way (different casing), but a clean slate was simpler to reason about than auditing what else depended on the old project.

## Gemini Files API instead of inline base64
First implementation sent the document as `inline_data` (base64 in the request JSON). This has a hard ~20MB payload ceiling and, worse, held the full base64-inflated string (plus a `JSON.stringify` copy of it) in the edge function's memory — hit `WORKER_RESOURCE_LIMIT` on a 13.6MB real file. Switched to Gemini's Files API: upload raw bytes once, get a `file_uri`, reference it in `generateContent` instead of inlining. Raises the ceiling to 2GB and avoids materializing a base64 copy at all. This fixed the memory problem — it did **not** fix the wall-clock problem (see next entry); those turned out to be two separate issues discovered in sequence, not one.

## Async (202 + background task) AND chunking — not bigger timeouts
Confirmed by direct measurement that the synchronous `extract` function times out at 150.9s wall-clock on the real 13.6MB test file — not a synthetic estimate. Then confirmed via a throwaway probe function that `EdgeRuntime.waitUntil()` (Supabase's background-task mechanism) does **not** grant a new time budget — a background task dies at the same ~150s ceiling as a normal request. This means:
- There is no config knob to raise the timeout — it's a platform ceiling.
- Async (return `202`, do the work in the background, client polls) is necessary regardless, so a slow extraction doesn't block the browser/hold an HTTP connection open.
- Async alone is **not sufficient** for real 200-400 page DRHPs, whose extraction time will itself exceed 150s even in the background. Chunking (deterministic page-range splits, each an independent extract job under the ceiling, merged in via the existing conflict-detection machinery) is still required and not yet built.
This is explicitly not RAG-style chunking — no embeddings, no similarity search, no retrieval. Just splitting one document into N page ranges and treating each as its own proposer into `merge()`, which was already built to accept multiple independent proposals into one fact set.

## merge() canonical in `supabase/functions/_shared/merge/`, `src/lib/merge/` re-exports
Originally `merge()` lived only in `src/lib/merge/` (the Vite/React side) and ran client-side after the extract function returned its result over HTTP. Once extraction became async, the client is no longer involved in persisting the result — the background task itself has to call `merge()` and write to the DB. That meant the Deno runtime needed to run this code directly, not just receive its output.
Considered three options: (1) copy the logic into `_shared/` — rejected, two sources of truth for the single most correctness-critical piece of this build is exactly where subtle bugs hide; (2) import maps / cross-directory relative imports with explicit `.ts` extensions — this is what was actually done, see below; (3) duplicate everything including types — used as a narrower fallback for pure type declarations only (see next entry), not for logic.
The relocation works because both Vite (`allowImportingTsExtensions: true`, already set) and Deno accept relative imports with explicit `.ts` extensions — so `src/lib/merge/merge.ts` is now a two-line re-export pointing at the canonical file. Verified by running the existing 18 tests unchanged against the relocated implementation — that was the acceptance bar, not just "it compiles."

## Type declarations ARE duplicated (`factsTypes.ts`), logic is not
Deno can't resolve the `@/` path alias `src/types/facts` uses, and reaching those files via a relative path from `supabase/functions/` was avoided as an added layer of cross-runtime fragility on top of the merge relocation. Instead, `supabase/functions/_shared/factsTypes.ts` is a hand-maintained structural mirror of `Field`/`FieldStatus`/`IssuerFacts`/the six domain interfaces. TypeScript's structural typing (not nominal) means two independently-declared interfaces with identical shape are mutually assignable, so this works without casting anywhere. The risk this accepts: if Task 2's fact shape changes, this file must be updated by hand — nothing enforces the two staying in sync. Considered acceptable because type declarations can't have *behavioral* bugs the way duplicated logic can; a drift here surfaces immediately as a compile error at the point of use, not a silent runtime divergence.

## Optimistic concurrency (version column) over row locking
Once extraction runs as a background task — and especially once chunking makes it inherently concurrent — multiple writers can read-modify-write the same `projects` row and silently clobber each other (last write wins, earlier merge's conflicts/facts vanish). Considered `select ... for update` (a real Postgres lock) vs. a `version` integer column with compare-and-swap retry. Chose optimistic concurrency: no long-held locks from a serverless/edge function (which could die mid-transaction and leave a lock stuck), simpler to reason about, and retries are cheap since `merge()` is fast and pure. Retry loop caps at 5 attempts before giving up and marking the document `failed` rather than retrying forever.
Known gap: `useUpdateFacts` (human edits, Task 4) does not participate in this scheme yet — see `docs/STATE.md`'s open decisions.

## Task 11 built ahead of a clean confirmed dataset (human call, 2026-08-09)
Before Task 11, checked the live project's facts against what its computed sections need. Found two blockers: zero fields anywhere are `status: 'confirmed'` (526 `ai`, 100 `empty`, 1 `edited`), and the singleton project's facts are contaminated — `company.legalName` reads "VERITAS FINANCE LIMITED" while `company.industry` reads "Topical Generics Pharmaceuticals", meaning two unrelated companies' test uploads merged into one project's fact set. Project facts/conflicts/merge_events were wiped back to empty (CAS-conditioned, version bumped 23→24) since re-confirming fields against contaminated data would be worse than starting clean.
Attempted to source a genuine 30–50 page demo document by slicing pages 1–40 out of the existing 540-page test PDF (`1785756069624.pdf` — turned out not to be the 30–50pg file it was assumed to be). **Paused before calling Gemini**: the Gemini quota decision (buy API credits vs. commit to a smaller document) is still open, and extracting anything now risks spending quota against the wrong choice. No extraction has run since the wipe — the project's facts are currently genuinely empty, not just logically reset.
**Decision:** don't block Task 11's code on having live confirmed data. Built `src/lib/templates/` against the known `IssuerFacts` schema, reading `status === 'confirmed'` exactly per the original architecture spec (not relaxed to any-status — see the Task 11 gap-check conversation for why an empty screen beats a contaminated one). It will render nothing until fields are actually confirmed post-extraction, which is expected and correct, not a bug to chase.

## Polling over Supabase Realtime
Client picks up extraction progress via `refetchInterval` (3s) rather than a Realtime subscription. Realtime needs replication enabled on the table plus its own RLS policies — another moving part that can break independently, for a UX difference (3s vs. instant) nobody will notice on a document that takes 10s–150s to process. Revisit if/when the UX actually calls for sub-second updates.
